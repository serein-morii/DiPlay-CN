# DiPlay 0.2.18 — 2026-10-11

Public preview for compatible BYD Android head units. Android 7.1+ (API 25) remains the minimum; Android 7.1–8.1 still needs vehicle testing. This update focuses on wired USB stability, connection messages in every language, steering-wheel keys on more head units and a settings backup. USB and wireless remain available, subject to the head unit's firmware and hardware.

## Highlights

- Wired CarPlay no longer drops every few minutes when a USB read finishes just as DiPlay stops waiting for it. Wired CarPlay also starts on Android 7.1 head units, on head units whose USB audio driver held the iPhone, and on head units without a VPN permission dialog when network ADB is approved. Related: [#610](https://github.com/shihabal3amri/DiPlay/issues/610), [#557](https://github.com/shihabal3amri/DiPlay/issues/557), [#518](https://github.com/shihabal3amri/DiPlay/issues/518), [#604](https://github.com/shihabal3amri/DiPlay/issues/604). [#625](https://github.com/shihabal3amri/DiPlay/pull/625), [#614](https://github.com/shihabal3amri/DiPlay/pull/614), [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- Fewer short music dropouts: the music decoder no longer throws away sound after waiting only 10 ms. Related: [#381](https://github.com/shihabal3amri/DiPlay/issues/381). [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- The connection screen shows the real stage and failure in every app language, and wireless CarPlay stops with a clear message on head units whose Android Bluetooth cannot reach the iPhone. [#624](https://github.com/shihabal3amri/DiPlay/pull/624), [#590](https://github.com/shihabal3amri/DiPlay/pull/590)
- Steering wheel: next and previous change CarPlay tracks on the CarPlay screen without the wheel-key service, for example on DiLink 2.0 without ADB; Geely/Lynk `geely_fx11` head units get wheel media keys and Siri; and wheel keys stuck on "Allowed, starting…" recover without restarting DiPlay. [#600](https://github.com/shihabal3amri/DiPlay/pull/600), [#626](https://github.com/shihabal3amri/DiPlay/pull/626), [#622](https://github.com/shihabal3amri/DiPlay/pull/622), [#625](https://github.com/shihabal3amri/DiPlay/pull/625)
- Back up and restore settings from a phone through a QR code in **Settings → About**, and install updates with another installer, such as MT Manager, when the head unit's own installer refuses. [#598](https://github.com/shihabal3amri/DiPlay/pull/598), [#593](https://github.com/shihabal3amri/DiPlay/pull/593)
- New experimental options, all off by default: Harman full screen, square corners without a safe area, clearer navigation voice over USB, MediaTek low-latency decoding, a media-key audio focus opt-out, car phone audio for calls, a cluster speedometer and FCE cluster guidance. Test them while parked.

## Connection setup and recovery

- Switch the iPhone into wired CarPlay mode when a head-unit kernel driver holds its USB audio interface. On an 8227L head unit (Android 9), `snd-usb-audio` claimed interface 0 of the iPhone's audio configuration, Linux refused every switch to configuration 6, and DiPlay failed with "Android could not claim the NCM interface 3" ([#518](https://github.com/shihabal3amri/DiPlay/issues/518)). When Android refuses the switch, DiPlay now detaches the head unit's drivers from the iPhone's current configuration and tries again. The report records the outcome as `USB configuration select target=6 ok=… before=… detached=… after=…`, and an iPhone that stays in another configuration now fails with that cause instead of the NCM claim error. Pending in-car acceptance. [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- On head units with no VPN consent dialog, wired CarPlay stopped at "This head unit cannot open VPN authorization" ([#604](https://github.com/shihabal3amri/DiPlay/issues/604)). When the car's network ADB is already approved, DiPlay now allows its VPN through it (`appops set … ACTIVATE_VPN allow`) and continues. It never asks for ADB approval at that point. The report logs `VPN consent over adb access=… granted=…`. Pending in-car acceptance. [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- Wireless CarPlay on a Ford SYNC+ head unit (i.MX8, Android 8.1) failed at the first Bluetooth message with "Bluetooth RFCOMM write failed": the message was written, but the head unit's security policy refused Android's flush of the Bluetooth socket ([#582](https://github.com/shihabal3amri/DiPlay/issues/582)). DiPlay now stops flushing a socket that refuses it and keeps the link; the report notes `Bluetooth RFCOMM flush refused by the head unit`. Other write and flush failures still end the attempt. Pending in-car acceptance. [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- When an iPhone on iOS 12 or 15 refuses wired CarPlay mode, the report now shows the three bytes it returns for its USB mode instead of `unreadable(3)` ([#509](https://github.com/shihabal3amri/DiPlay/issues/509), [#455](https://github.com/shihabal3amri/DiPlay/issues/455)). [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- Fix wired CarPlay on Android 7.1 head units, where every attempt stopped at the USB network step with `SocketException: Invalid argument at PlainSocketImpl.socketBind` ([#557](https://github.com/shihabal3amri/DiPlay/issues/557)). The AirPlay listener on the wired address `fe80::2` named no network interface. Android 8 and later add the interface themselves, and Android 7.1 does not, so Linux rejected the listener. DiPlay now binds it to the VPN tunnel that owns the address, and the log records the choice as `wired AirPlay listener scope iface=tun0 index=…`. Pending in-car acceptance. [#614](https://github.com/shihabal3amri/DiPlay/pull/614)
- Retry restoring the wheel-key service when the car's ADB is not reachable yet, about every 10 s for a minute. A single early attempt at boot left the keys on "Allowed, starting…" until DiPlay was force-stopped ([#606](https://github.com/shihabal3amri/DiPlay/issues/606), [#619](https://github.com/shihabal3amri/DiPlay/issues/619)). The diagnostic report now has a `Wheel key service:` line: whether the service is wanted, allowed and bound, and the last restore attempt. Pending in-car acceptance. [#622](https://github.com/shihabal3amri/DiPlay/pull/622) DiPlay now also checks each time its settings or the CarPlay screen comes back to the front, so keys stuck on "Allowed, starting…" while the car's ADB works no longer need a restart of DiPlay ([#606](https://github.com/shihabal3amri/DiPlay/issues/606)). [#625](https://github.com/shihabal3amri/DiPlay/pull/625)
- Wired CarPlay no longer drops every few minutes with "Android could not cancel timed out USBMUX read request". A USB read that finished just as DiPlay gave up waiting for it could no longer be cancelled, and DiPlay ended the whole session instead of keeping the data. Reports from a Hyundai head unit with a Telechips chip and from a DiLink 5.1 car showed it ([#610](https://github.com/shihabal3amri/DiPlay/issues/610), [#301](https://github.com/shihabal3amri/DiPlay/issues/301)). DiPlay now takes the finished read back and keeps its bytes. Pending in-car acceptance. [#625](https://github.com/shihabal3amri/DiPlay/pull/625)
- The car hotspot details warn when the name contains Chinese or other non-English characters. Two Song PLUS/Song L owners found CarPlay stayed on "Getting CarPlay ready…" until they renamed the car hotspot in English ([#303](https://github.com/shihabal3amri/DiPlay/issues/303)). [#622](https://github.com/shihabal3amri/DiPlay/pull/622)
- The connection screen shows the real stage and failure in every UI language. In Chinese and the other translations, every stage and failure read "Getting CarPlay ready…" while the connection failed and retried, as in the Android 7.1 reports in [#557](https://github.com/shihabal3amri/DiPlay/issues/557). [#624](https://github.com/shihabal3amri/DiPlay/pull/624)
- On head units whose Android Bluetooth reports connections that reach no phone, because calls and music run on the maker's own module, wireless CarPlay now stops with that cause and suggests USB instead of retrying the same failure ([#354](https://github.com/shihabal3amri/DiPlay/issues/354)). A link that connected in under 50 ms and delivered no byte is tested with a connection to a service no phone offers; only when that also succeeds at once is the link called unusable. The report records `Bluetooth link check …`. [#590](https://github.com/shihabal3amri/DiPlay/pull/590)
- With several iPhones paired, wireless CarPlay also finds the connected one through the head unit's A2DP sink and hands-free client profiles, where a head unit sees the iPhone. [#585](https://github.com/shihabal3amri/DiPlay/pull/585)
- On Android devices without BYD's SOME/IP gateway, DiPlay no longer tries to bind it three times a second. [#587](https://github.com/shihabal3amri/DiPlay/pull/587)

## Audio, calls and Siri

- Fix short music dropouts. While DiPlay waited for the car to play queued sound, the music decoder filled up and DiPlay discarded the next AAC packet after waiting only 10 ms, cutting about 21 ms of sound. A DiLink 3.0 report lost 80 packets in one drive, roughly one every 10–20 s; reports from DiLink 5.0 and a Harman head unit also lost some ([#381](https://github.com/shihabal3amri/DiPlay/issues/381)). DiPlay now plays the decoded sound and keeps waiting up to 0.5 s, as the video decoder already did. `decoderDroppedTotal` in the report counts any packet still dropped. [#618](https://github.com/shihabal3amri/DiPlay/pull/618)
- The diagnostic report compares the playback position DiPlay reports to the iPhone with the newest audio it received: `Audio: feedback type=… reported=… received=… aheadMs=…` once per stream, and again with `overrun=true` whenever the position runs more than 0.1 s past the received audio. This tells a stream that starved apart from one the iPhone stopped for another reason ([#620](https://github.com/shihabal3amri/DiPlay/issues/620)). Playback is unchanged. [#625](https://github.com/shihabal3amri/DiPlay/pull/625)
- Experimental and off by default: **Settings → Advanced → Clearer navigation voice over USB**. Over USB the iPhone sent navigation prompts as 8 kHz audio, the lowest rate DiPlay offered ([#148](https://github.com/shihabal3amri/DiPlay/issues/148), [#341](https://github.com/shihabal3amri/DiPlay/issues/341)). The option stops offering 8 and 16 kHz for prompts and alerts; phone calls are unchanged. The report's `Audio: starting … rate=` line shows the rate the iPhone chose. Not yet tested in a car. [#622](https://github.com/shihabal3amri/DiPlay/pull/622)
- Experimental and off by default: **Settings → Advanced → Disable media-key audio focus**. For head units that send their physical volume keys to the app holding audio focus, so the volume keys stopped working while CarPlay played (reproduced on a Changan S202, Android 9). Steering-wheel media keys may stop working on head units that need focus. Applies at the next connection. [#615](https://github.com/shihabal3amri/DiPlay/pull/615)
- Experimental and off by default, under **Settings → Advanced**: **Car phone audio for CarPlay calls** and **Car phone audio for VoIP calls in other apps** hold a Telecom call so the car's own echo cancellation handles the call ([#18](https://github.com/shihabal3amri/DiPlay/issues/18)). Measured on a DiLink 3 Han with a test app, not yet with a real CarPlay call; the caller's voice can come out louder. See [BYD navigation](BYD_NAVIGATION.md#car-phone-audio-experimental). [#595](https://github.com/shihabal3amri/DiPlay/pull/595)

## Display

- Experimental and off by default: **Settings → Advanced → Display (experimental) → Harman head-unit full screen** lets CarPlay use the side panel where Harman firmware keeps its clock. It was confirmed with an earlier build on a Great Wall ORA Good Cat (Harman, Android 8.1, 32-bit x86) ([#603](https://github.com/shihabal3amri/DiPlay/issues/603)). The APK now also contains 32-bit x86 native libraries. [#613](https://github.com/shihabal3amri/DiPlay/pull/613)
- Off by default, in the in-car menu under **Safe area**: **Square corners, no safe area** asks the iPhone for a full-screen picture with square corners. Try it on screens where CarPlay leaves a strip at an edge or shows the wallpaper color in its rounded corners ([#578](https://github.com/shihabal3amri/DiPlay/issues/578), [#586](https://github.com/shihabal3amri/DiPlay/issues/586)). The saved safe area is not used while it is on. [#596](https://github.com/shihabal3amri/DiPlay/pull/596)
- The in-car menu's **Physical length** moves in 25 mm steps instead of 50 mm. iOS changes CarPlay's layout only at certain screen sizes, and 50 mm steps could jump past the size a driver wanted ([#489](https://github.com/shihabal3amri/DiPlay/issues/489), [#591](https://github.com/shihabal3amri/DiPlay/issues/591)). [#622](https://github.com/shihabal3amri/DiPlay/pull/622)
- A custom car-button icon is sent to the iPhone at 192 pixels, like the built-in one. It was sent as a 1024-pixel PNG, which can be megabytes for a photo, inside the reply the iPhone reads while connecting. After a Ford owner replaced the icon, CarPlay no longer connected ([#567](https://github.com/shihabal3amri/DiPlay/issues/567)). The report logs `CarPlay car-button icon resized` when it scales one. [#622](https://github.com/shihabal3amri/DiPlay/pull/622)
- Experimental and off by default on MediaTek head units: **Settings → Advanced → MTK decoder low latency**. Asks MediaTek decoders for their own low-latency modes on the main CarPlay picture and falls back step by step when a decoder refuses them; the report's `decoder=` line shows the mode used. Applies at the next connection. [#608](https://github.com/shihabal3amri/DiPlay/pull/608)
- Experimental and off by default, with **CarPlay map on dashboard**: **Cluster speedometer** draws the vehicle speed over the dashboard map, read through the car's approved ADB, with position, size and opacity controls. On a Song Pro (DiLink 3.0) the dashboard map hides the car's own speed ([#423](https://github.com/shihabal3amri/DiPlay/issues/423)). [#607](https://github.com/shihabal3amri/DiPlay/pull/607)
- The CarPlay waiting screen and the in-car menu use DiPlay's button style, with a focus ring for remote and D-pad use. [#594](https://github.com/shihabal3amri/DiPlay/pull/594)

## Vehicle

- With **CarPlay call keys (experimental)** on, the wheel's next-track key answers and previous-track declines while a CarPlay call rings. The Song Pro DM-i's wheel has no dedicated answer key ([#272](https://github.com/shihabal3amri/DiPlay/issues/272)). The keys skip tracks as before at all other times. [#622](https://github.com/shihabal3amri/DiPlay/pull/622)
- Show CarPlay arrows and the next-turn distance in the cluster's navigation view on head units built on the FCE/Coagent T7 platform, through their stock `fce_misc_service_hal_property` service, without ADB. Off by default: turn on **Guidance in the FCE cluster (experimental)** in the **Navigation on HUD and dashboard** card, which now also appears on these head units. See [BYD navigation](BYD_NAVIGATION.md#cluster-guidance-on-fce-head-units-needs-no-adb). The property path was confirmed in a car with Android Auto guidance; this CarPlay integration has not yet run in a car. [#599](https://github.com/shihabal3amri/DiPlay/pull/599)
- The steering wheel's next and previous keys change CarPlay tracks while the CarPlay screen is in front, without the wheel-key service, which DiLink 2.0 units without ADB cannot turn on ([#519](https://github.com/shihabal3amri/DiPlay/issues/519), [#602](https://github.com/shihabal3amri/DiPlay/issues/602), [#611](https://github.com/shihabal3amri/DiPlay/issues/611)). Not during calls. [#600](https://github.com/shihabal3amri/DiPlay/pull/600)
- Steering-wheel play/pause, next and previous, and a long press on the voice key for Siri, on the Geely/Lynk & Co `geely_fx11` head unit (DesaySV, Android 11), through the car's own input service ([#149](https://github.com/shihabal3amri/DiPlay/issues/149)). Siri uses the voice-communication microphone there, the only source that firmware opens. The car's HiCar app keeps the long press until it is disabled; see [compatibility](COMPATIBILITY.md). [#626](https://github.com/shihabal3amri/DiPlay/pull/626)

## Settings

- About now opens inside Settings like the other categories. On wide screens the category rail stays visible, and About is the last entry in it. The page uses the same title style. [#597](https://github.com/shihabal3amri/DiPlay/pull/597)
- Installing an update no longer opens Android's "install unknown apps" page first, which some head units answer with "Not supported yet". With more than one installer, such as MT Manager, DiPlay asks which one to use, and it uses the public Downloads copy when that still matches the verified file. The report records `lastInstall=`. [#593](https://github.com/shihabal3amri/DiPlay/pull/593)
- **Settings → About → Back up or restore on a phone** shows a QR code for a page on the head unit, where a phone exports the settings as a file or imports one. Only listed settings travel: pairing keys, authentication, and the car's hotspot name and passphrase never do. The page stops when it is left or after 10 minutes without use. [#598](https://github.com/shihabal3amri/DiPlay/pull/598)

## Updating and reporting problems

Install the official APK over the previous public release to preserve settings and pairing records. The package remains `com.shihab.diplay`; release packaging verifies the existing signing certificate. Source builds omit runtime authentication assets by default; see [building from source](BUILD.md).

Reproduce remaining problems on **0.2.18**, then open **Settings → Diagnostics → Save diagnostic report**. Android 10+ normally saves to **Downloads/DiPlay**; on Android 7.1–9, DiPlay asks for storage access and saves there too. If it is unavailable, follow the save confirmation and use **View report** or **Share**. Review the `.txt` and attach it to a matching [existing issue](https://github.com/shihabal3amri/DiPlay/issues) or [new issue](https://github.com/shihabal3amri/DiPlay/issues/new/choose). Connection reports require the diagnostic log. Reports are not uploaded automatically.

Include car/head unit, Android/DiLink and full firmware, iPhone/iOS, USB or wireless mode, relevant settings, reproduction steps and failure time.

See [validation](VALIDATION.md) for automated checks. No new maintainer vehicle test of the complete release is claimed. The wired fixes, the music dropout fix, the Bluetooth link check, the wheel-key changes, the settings backup and the experimental options above need current in-car feedback; test optional features while parked.

Thanks to the contributors linked in the 22 pull requests above, and to the users supplying diagnostic reports and vehicle feedback.
